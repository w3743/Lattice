用户将项目目标改为研究 Lattice 如何与嘉立创 EDA 专业版最新版协作，后续原理图尽量采用嘉立创格式，取消 PDF 输出。

- 使用 Python `subprocess.run` 捕获 Windows 客户端输出，`doctor` 返回 `ok=true`、`connected=true`、`versionMatch=true`。这证明本地桥接可达，不等于已完成工程生成或回读。
- 官方[CLI 文档](https://prodocs.lceda.cn/cn/api/guide/cli.html)介绍命令行、MCP、扩展 API 和 `.eprj3` 文件夹工程。浏览器版不具备这套桌面桥接能力。

接口盘点如下；其中原理图创建、真实库检索、网表和原生归档往返已通过下述样例实测，PCB 操作尚未执行：

## 协作路线与完成标准

**首选桌面 CLI 调用官方扩展 API。** Python 继续处理 PBDL、`CircuitGraph`、仿真和约束评价，嘉立创处理库与编辑器对象。先做一个小型原理图往返，不新增一套 EDA 编辑器，不重写 PCB 布局布线。CLI 与 MCP 只是同一能力的不同调用入口，初期使用 CLI 即可。

**文件交换采用客户端原生输出。** 优先由客户端生成并导出 `.epro/.epro2`；`.eprj3` 适合作为后续可审查的文本工程，但须先验证本机打开、保存与双向同步。旧的“标准版 JSON → Chameleon → 专业版”只作为兼容回退，不能继续绑定旧转换器哈希作为最新版协议。参见官方[专业版工程导入导出说明](https://prodocs.lceda.cn/cn/import-export/import-lceda-pro/)。

模型与库器件必须分开：`builtin:nmos` 这样的仿真原语并不是可采购 MOSFET，不能凭符号相似就补一个料号。缺少真实器件绑定时，应保留为明确的仿真/抽象器件，并报告不能转入 PCB 的原因。器件选择需独立核对数据手册引脚、封装焊盘及板外器件属性。

首个协作闭环的完成标准：

1. 在隔离样例工程中将一个现有小电路映射为嘉立创器件，完整保存位号、值、引脚及网络。
2. 导出原生工程后重新打开，从最终文件/客户端回读；逐项比较引脚网络与库引用，不以文件存在作为通过。
3. 获取原理图 DRC 结果、网表与 SVG/PNG 预览；规则问题逐项解释，物理性能由 Lattice 的独立仿真结论支持。
4. 交付原生工程及必要的机器可读验证结果，**不生成 PDF**。小型样例已完成文件与网络往返、警告解释及可复用导出；自动器件选型和生产验证不属于已完成能力。

## RC 原生往返实测（2026-10-04）

已通过本机官方扩展 API 放置 R1（C21190，1kΩ，R0603）和 C1（C14663，100nF，C0603），读取实际引脚坐标后连接。元件料号只是本次库映射样例，未作全温、容差或制造资格验证。

流程为：复制官方示例到隔离输出目录作为 CLI 启动载体 → API 新建本地工程 → 创建器件、导线和端口 → 保存并导出 `.epro2` → API 导入为另一个本地工程 → 关闭会话 → 将导入的 `.eprj2` 复制到工作区 → 新会话重新打开并导出网表。未修改用户原有工程。

可查看的原生工程为 [`lattice_rc.epro2`](../outputs/lceda_probe/lattice_rc.epro2) 与 [`lattice_rc.eprj2`](../outputs/lceda_probe/lattice_rc.eprj2)，预览为 [`lattice_rc.svg`](../outputs/lceda_probe/lattice_rc.svg)。同目录 `verification.json` 记录结果与产物哈希，`graph.json` 是独立的期望连接模型。

- **PASS：网络与属性往返。** 重新打开后的 `R1-1→IN`、`R1-2/C1-1→OUT`、`C1-2→GND` 四个引脚全部匹配；位号、完整料号、LCSC 编号、值与封装匹配。导出前后 Protel2 网表解析结果完全相同。
- **PASS：原生库引用。** `.epro2` 包含 6 个器件文档、6 个符号和 2 个封装（包括图框、端口与地标识）；回读对象的器件、符号、封装引用均能在归档内解析。
- **PASS：指定理想模型。** Lattice 对 1Hz–1MHz 共 101 点的 RC 传递函数与解析式比较，最大复数误差 `2.22e-16`，截止频率约 1591.55Hz。激励为外部理想 1V AC 源，不是遗漏的板上器件；结论不覆盖实物容差、寄生与 PCB。
- **未通过严格 DRC：2 项已解释 warn。** 本机 `SCH_Drc.check(true,false,true)` 只返回聚合数量；打开本样例的 DRC 面板后，可通过 CLI 只读访问 `parent.document` 内的日志元素取得详情。原来的第三项是重复 `IN` 名称属性，已通过重建对应导线修复，未关闭规则。剩余两项分别是 `IN`、`GND` 各只连接一个器件引脚，符合本次外部激励/参考端口的模型边界；这不等于板上连接器或电气验收已完成。

[`circuit_ai/lceda.py`](../circuit_ai/lceda.py) 从客户端 Protel2 网表核对整个 `CircuitGraph`，显式要求逻辑端子→物理引脚映射；拒绝漏脚、额外引脚、交换网络、隐式合并网络和物理焊盘网络冲突，并检查 `.epro2` 内的器件/符号/封装引用。真实客户端回读样本保存在测试 fixture 中。

实际自动化产物：[原生归档](../outputs/lceda_export_rc/design.epro2)、[本地工程](../outputs/lceda_export_rc/design.eprj2)、[SVG](../outputs/lceda_export_rc/design.svg)。归档内有 3 个器件文档、3 个符号、2 个封装（包含图框）。导入前后器件属性和四个引脚网络完整一致；同目录 `verification.json` 明确保留严格 DRC 未通过和器件模型等价性未验证状态。

运行针对性检查：`python -m pytest tests/test_lceda.py tests/test_lceda_export.py -q -p no:cacheprovider`。这条入口支持显式绑定后的结构交付，不承担自动选型、器件宏模型匹配、自动布局布线、PCB 可制造性或全工况验收；尚未将任意 PBDL 综合结果自动映射到可采购器件。缺少绑定或存在参数变量时明确拒绝，不借用外观相似的器件代替。

本机接入时需处理的已验证差异：

- `importProjectByProjectFile` 的 `Offline Client Local Path` 出现在 API 文档和包装层，但当前编辑器处理层未实现，实际调用没有生成文件。离线模式下使用 `New Project`、以当前工程的 `teamUuid` 指向本地工程目录，导入成功。每次必须检查返回工程、磁盘文件与回读结果，`ok=true` 不足以说明操作完成。
- `createNetLabel` 返回 `null` 仍可能已创建属性；应回读对象确认，不能直接重试，否则产生重复标签。指定 net 的 `create` 导线本身已生成名称属性。
- 编辑操作与查询不总是同步：同一次调用立即查询可能得到旧对象列表。导出前须等待同步并核对对象数。
- 文本网表应以原始字节保存；Windows 下将含 CRLF 的文本再次用默认 `write_text` 写入会变成双换行，破坏属性键值配对。

## 历史交付经验

以下记录来自一次真实电机驱动交付，保留其版本与工况边界。

## 生成与交付

- **原厂资料与库引脚分开核对。** 先按原厂数据手册确认器件引脚功能、额定值和推荐接法，再独立核对嘉立创符号、封装焊盘编号及映射。库记录只能说明库里怎么画，不能证明设计接法正确。
- **物理多焊盘合并须检查网络冲突。** 一个逻辑引脚映射到多个物理焊盘时，逐个焊盘展开网络；同一物理焊盘若被映射到不同网络必须报错。只有厂家明确允许不连接的脚才能标NC；重复电源焊盘和散热焊盘不能因为符号没画出就省略。
- **输出文件要形成闭包。** 工程内应包含器件、符号、封装的全部引用；板外器件标明并设置为不转 PCB。交付前从最终 `.epro` 回读每个器件和引脚，比较位号、器件型号、封装、网络、焊盘编号与几何，并确认未连接脚以原生 NC 属性保存。只检查生成前的中间数据不够。
- **官方转换器也要做输入边界验证。** 本次标准版到专业版转换遇到 Node `Buffer` 底层数组可能大于有效切片的问题：转换端把整个 `ArrayBuffer` 当作文件时会读到多余尾部。兼容处理应只对转换子进程复制有效字节，不改安装文件；并记录转换器版本/哈希、输入输出哈希和转换结果，转换器升级后重新验证。
- **预览需验证中文和页面比例。** SVG/PNG 应检查实际渲染，按原始视图框保持比例；文本抽取正确不能替代逐页视觉核对。当前交付约定已取消 PDF。
- **区分解析、导入和电气验收。** 网表解析器通过，只能说明特定解析器读懂了文件并得到预期字段；不能证明嘉立创客户端确认导入成功、ERC通过、PCB可制造或电路安全。界面导入、ERC、布局布线和实机测试应分别记录。

## 电路复核与仿真边界

- 行为级仿真适合检查已建模的拓扑、控制逻辑和指定暂态；它不能代替真实器件宏模型、开关损耗、热路径、容差、寄生参数及短路/失控等故障工况验证。缺少模型的项目必须列为未验证，不能把理想源或理想开关仿真写成器件通过。
- 本次复核发现 LM5164 的 RON 定时电阻接在 AUX_IN 与 RON 之间，而器件推荐接法要求由 RON 接定时电阻到 GND；这是实际接线问题，**该次历史审查时尚未整改；最新状态见下文RevD**。
- 本次复核还发现 DRV8353 栅极供电预算存在缺口：按当前 MOS 配置、20 kHz 和数据手册栅极电荷估算，单组开关管的典型栅极充电电流已贴近/超过驱动器供电能力，最坏值及栅极下拉电阻电流会进一步增加需求。需联合确认开关频率、电机极对数、栅极电阻、母线电压和驱动器能力，并以实测波形验证；**该次历史基线未通过，不能将其检查外推到后来版本**。
- 工况结论要给边界和假设。至少覆盖输入电压范围、负载/电流、启动、堵转、再生、急停、过温、欠压和控制器失效；电池/BMS、热阻、电机参数未知时明确标成条件项，避免用单一额定点外推“适用于所有工况”。

## Lattice 的适用范围

Lattice 当前的线性 MNA 可辅助核算电阻分压和线性滤波，`OperatingEnvelope` 可枚举声明范围内的输入电压与负载角点。这些结果可作为审查证据的一部分；它们没有覆盖本电机驱动的完整三相 FOC、功率器件开关/热模型、嘉立创原理图生成与 PCB 自动布线，不能据此声称已经具备完整 FOC 仿真或自动 EDA 后端。

## RevD整改更新（2026-09-24）

FOC连接源现已改为404个位号，361板上/43板外、39种内嵌封装、27页原理图；1072个连接节点与24个NC回读一致。当前状态见FOC项目“整改说明.md”，上述300位号和失败场景属于整改前历史，保存在缓存归档。

实际修正了RON接地、栅极供电预算、自动预充、独立心跳看门狗和备用泄放。发现新版本必须重新计算关联链：提高辅助欠压门限后，稳压最低输出要留下纹波裕量；备用电源从预充母线取电会影响最终可达电压，不能只用空载RC曲线。预充比较器全温偏置也必须计入。

公共库查到型号并不代表封装可直接使用：TPS3431符号引脚可用，但其EP尺寸与TI推荐图不一致，最终以原厂焊盘本体修正，PCB阶段仍需地铜/焊膏工艺复核。

ngspice共享库不会自动按安装目录载入所有spinit组件：PSpice模型需设置兼容模式，并显式载入XSPICE code models。命令返回0不代表加载成功，要检查日志；带空格路径的引号处理也应验证。修复解析后LM5164模型仍遇数值收敛问题，因此没有宣称启动通过。行为仿真通过不能替代这个失败项。

用户随后明确：30kg履带车，两台电机各1800W、一板一电机、4倍减速暂算、主动轮60mm；无机械刹车是既定架构。此前强加机械刹车门槛属于需求推断错误，已从许可代码/交接资料撤销。19项静态/行为判据包含双路失效预期负对照，仍不能解释成车辆19工况安全。应验证电子制动及故障运动边界，不能擅自把某种制动实现写成用户硬约束。硬件自动化系统必须区分“文件生成”“指定模型满足判据”“实际车辆可用”，不能由多个局部通过累加出整机安全结论。
